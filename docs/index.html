first decision

Three lines, then your existing call.

# not on PyPI yet
pip install -e /path/to/tierwise
from tierwise import Router, TaskSignals

router = Router()
decision = router.route(TaskSignals(category="bugfix", file_count=4, lines_changed=150))

client.messages.create(model=decision.model, ...)  # unchanged

decision.model is a plain string. TierWise never makes the call — which is why any provider works. Model names live in a tierwise.toml you commit, so CI, the tuning cron and every developer resolve the same ones: 

$ tierwise models
low     gpt-5-mini                   [config]
medium  llama-4-70b                  [config]
high    claude-opus-4-5              [env]
the score

Category is a weak signal. Context is not.

“Write a unit test” is fifteen lines or a six-hour slog through mocked dependencies. What predicts difficulty is everything around the label, so category only breaks ties — it never drives the decision.

signalcontribution
files touched1 / 2–3 / 4–10 / >10 → 0, 1, 2, 3
lines changed<20 / <100 / <400 / ≥400 → 0, 1, 2, 3
dependency depth0 / 1–2 / >2 → 0, 1, 2
needs existing context+1.5
ambiguity (0–1)×3.0 — the heaviest
greenfield−0.5
category−0.10 (typo) … +0.22 (debug prod)

Confidence is the distance from the nearest cut, and it is continuous. A score sitting on a cut has confidence 0 — which is exactly the task worth spending a cheap classifier call on. Everything else resolves for free. If confidence could only take a handful of values, a small threshold change would either do nothing or change everything, and the loop below could not work at all.

inner loop

The tier climbs for one hard step, then drops back.

A router that picks one tier per task recreates the problem one level down. Each step is routed on its own; a step that comes back wrong escalates without restarting the task. This is a real run of the bundled example:

step 0lowread the failing test
step 1hightrace across modules
step 2mediumtests fail →
step 2 retryhightests pass
step 3mediumpackage-wide rename
step 4lowchangelog entry

One escalation, three de-escalations. Illustrative spend $0.234 against $0.470 for sending every step to the top tier.

outer loop

Each cut moves on the failures of the tier it governs.

Outcomes you report go to a decision log. The tuner reads it, joins each decision to what happened, and moves the thresholds those decisions came from — per boundary, never on one aggregate rate: 

$ tierwise tune routing.jsonl --rework-cost 0.05
cost per successful step: $0.0167
  low_medium   n=12  fail=0.00  expl=6/4   target=0.22 [cost-derived]  0.30 → 0.33  relaxed
  medium_high  n=6   fail=0.67  expl=6/0   target=0.50 [cost-derived]  0.70 → 0.67  tightened

Two independent conclusions from one log, moving in opposite directions. Tuned values persist and load in the next run, and a watermark means re-running over the same log changes nothing — evidence is spent when it is acted on, not every time it is read.

Failure is asymmetric, and that is the hard part. Under-provisioning shows up in outcome data. Over-provisioning never does: the top tier does not fail work a cheap tier could have handled. So a fraction of steps can be deliberately routed one tier below the recommendation — expl=6/4 above means six downgrades tried, four succeeded. That is the only direct evidence that the cheap side has room. A downgrade that fails escalates straight back up.

before you rely on it

What it does not do.

01

It does not extract the signals. Nothing counts your files and lines for you yet — a git diff helper ships in the example, and ambiguity is still your judgement. Wrong signals in, wrong tier out.

02

It is only as good as your verifier. “The response was non-empty” gives you a loop that escalates on noise and then teaches the tuner from it. Point it at your tests.

03

The built-in model names are guesses. They are labelled default (unverified) for that reason. Set your own before the first call.

04

Three tiers is the model. That maps onto most small/mid/large lineups. Five meaningful sizes, or routing across providers by price, would be collapsing something finer.

05

Auto-applied tuning drifts on its own. Bounded — one step per run, floor, ceiling, every change logged — but real. Pass explicit thresholds to pin it, or tune with --dry-run and commit the changes yourself.
